# 如何构建数据分析智能体 🚀

项目中碰到的坑！

过去一年AI 在编程领域（如 Cursor, Claude code）的表现进步最快，因为在这个闭环内，自己开发、自己使用、自己测试并优化数据。过去几年行业内涌现了大量 Text-to-SQL产品。技术逻辑看似完美：用户提问 -> AI转译 -> 数据库执行 -> 返回结果。但在实际落地中，面临的问题远比想象的要多，这也是至今大部分产品定位在copilot。数据库里有表、有字段、有数据，但业务问题往往不是按数据库结构提出的。结合过去2~3年我们在产品和项目交付上踩过的坑，数据分析智能体要比其他智能体场景复杂。

统一语义层，这是目前所有厂家都会提到的概念，已经达到了共识。语义层主要为了让AI理解业务上下文，和数据字典、指标含义有一些区别。没有语义层，AI 很可能生成一条“看起来能跑”的 SQL，但结果并不是企业真正认可的业务答案。比如：在交通行业，按照国标GA 802-2014定义营运车辆，包含公路、公交、出租、旅游客运、租赁、危化品运输、教练、货运这几种类型，还有时候包含口语化定义例如百吨王即车辆重量和载货重量加起来百吨。在零售行业，以“销售额”指标统计为例，真正进入分析前，至少要明确：是否扣除退款？是否包含优惠券、满减、平台补贴？是按下单时间、支付时间，还是发货时间统计？是否排除测试订单、异常订单、内部订单？多渠道、多系统数据重复时，以哪个系统为准？在统一语义层，它至少要告诉 AI：表和字段在业务上表示什么。核心指标如何定义和计算。字段值、状态码、内部简称分别代表什么。哪些维度可以和哪些指标一起分析。哪些业务文档、分析习惯和专家经验需要被复用。不同用户在什么权限边界内使用数据。

多轮问答和临时数据上传问答，数据分析往往会根据问答层层下钻，这里涉及会话记忆，临时表和数据表碰撞问题，对于BI厂商来说可结合指标平台，而没有指标平台，数据分析的思维过程又容易发散，可能跳过某个问题又重新回来，所以复杂多步数据分析最后选择了可视化画布模式。在技术上，多轮问答要解决长上下文和跨工具上下文流转，然而本地化、商用部署大模型，受限于硬件资源、模型尺寸等原因，模型支持的序列长度往往相对较少（通常在几K到几十K之间），不足以支撑大数据分析场景下的中间查询结果流转，熟悉智能体context engineering的会进行摘要等处理方式，但里面的处理策略姚结合具体业务场景。口袋数据问答，这是业务场景需求比较多的地方，同上新上传表和数据表碰撞问题，单上传表问答比较容易实现。

意图识别任务拆分到表召回，AI意图识别进行任务拆分，选择进入复杂任务COT模式结果一般会比简单任务容易出错。表召回，是自然语言到Sql的前置模块，通过意图解析与Schema link筛选出最相关的表并对候选表排序打分，再将召回结果传入模型进行任务细划。所以表召回和语义层以及数据治理紧密相关。

多表查询，多表关联这个问题网上讲到的比较多，目前业界共识单表准确率较高，多表查询回到业务环境需要提升的地方很多，一般都是通过逻辑层进行要素关联或者大宽表，实际业务过程十几张表和几十张表复杂程度完全不一样。实际落地选择何时的方式也有很多方式，比如过程可选。

数据建模，比较重要的核心功能，一般业务问题不会是单个问答就能解决。通过画布讲单个问答卡片式逻辑组装关联，远比一个复杂问题要可靠多。

报告生成，当前基本主流厂商生成报告都是基于报告需求，先生成大纲，确认和编辑大纲后再生成具体报告，然后可以编辑和报告任务可定时。报告核心关注的数据分析结果和业务总结与建议，一般能结合业务知识库给出建议知道比较科学，但这条路目前落地还是比较曲折。

Sql过程可视化，AI的边界与"可验证性"工程，让业务团队可以用自然语言获得带来源、可核查的答案、图表和洞察。

大模型训练，当前会用到行业语料对大模型做一些训练，由于行业数据语料数据集有限和大模型生成代码能力已较强，私有化部署选择32B模型已够用。所以大部分都会选择数千条数据（包含数据增强工程）进行lora微调。实践下来，由于lora改动参数量很小，多做几轮实验会发现SFT微调对于行业知识的理解提升有限，所以更多是意图识别、表召回任务目标，比如schema-link方式。

数据权限问题，角色和权限管理是确保数据访问控制和安全性的关键部分。通过定义和管理角色及其对应的访问策略，可以精确控制用户对数据的访问权限，访问策略的工作原理是通过一系列的规则来确定用户对数据的访问权限。这些规则可以基于数据源、表、字段，甚至是数据行。访问策略如何工作的详细解释如下：

数据源级别控制：策略可以指定哪些数据源用户可以访问。

表级别控制：通过正则表达式匹配表名，策略可以控制用户对特定表的访问。

字段级别控制：策略可以指定用户是否可以访问特定字段，例如敏感信息字段。

行级别控制：通过行过滤器，策略可以控制用户对表中特定行数据的访问，通常与用户属性相关联，如用户ID。

结果展示，AI自动生成Sql结果展示带有随机性，展示关键字段会偏离业务核心关注需求，这些都是可以通过工程化解决的。

时间理解，大模型对于时间的理解，比如近7天，近1个月，这里涉及时间段的范围取值。

开窗函数，大模型对于Sql开窗函数的生成能力欠缺，尤其数据分析领域经常会用到的同环比。
